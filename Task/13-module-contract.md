# 13 — 模块契约（entity / service / manifest）

> **状态**: 待细化
> **依赖**: 12
> **阶段**: 远期架构

## 目标

把「一个生活域要接进这套 harness，到底得暴露什么」写成一份**通用契约**——从厨房模块反推出模板，让第二个模块照着填。

## 为什么做

远期愿景是 Home Assistant 式的**个人生活中枢**（厨房 + 衣柜 + 记账 + 资产 + 生日 + 订阅，统一一个 AI 交互口）。这个门类有成功范本，不是空想（[DESIGN.md](../DESIGN.md) §12.3）。

但它有一个必须选对的岔路：

| | 结果 |
|---|------|
| ❌ **单体巨石**（一套 schema 全塞一个库） | 造出 5 个浅薄 App 而不是 1 个好的，单人淹死在维护里 |
| ✅ **中枢 + 模块**（每域独立，只暴露「AI 可读状态 + agent 可调纯函数」） | 加模块的边际成本持续下降 |

> **关键认识：✅ 这一种正是现有 A 层 / B 层模式的推广。** 三档库存 + jsonb attributes + A 层纯函数留给 agent 调——**厨房模块其实已经是这个大愿景的「参考实现·第一个模块」**，这套模式的正确性已被一期验证。本任务只是把它**显式化**。

**为什么放在 [Task/12](./12-ai-command-layer.md) 之后**：契约必须从「真的被 agent 调过一遍」的经验里长出来。先在厨房上把 tool 定义、确认机制、记忆注入跑通，再抽象；反过来先抽象一定抽错。

## 契约要回答的问题

从 Home Assistant 的三件套反推：

| HA 概念 | 本项目对应 | 要定义什么 |
|---------|-----------|-----------|
| **entity**（`state` + `attributes`） | 三档 `stock_level` 就是极好的 `state`，`attributes` jsonb 就是 `attributes` | 每个域对象的统一表示：`{id, domain, state, attributes, timestamps}` |
| **service**（`light.turn_on`） | A 层纯函数 | 统一动作命名空间：`kitchen.set_stock_level` 等，自描述 schema 可直接生成 agent tool |
| **manifest** | 无 | 模块声明：名字、版本、暴露的 entity 类型、注册的 service、vault 目录结构、是否默认暴露给 AI |

## 关键决策（待讨论）

- [ ] entity 的统一表示怎么定，才既覆盖厨房（库存/菜谱/日历）又不至于抽象到没用？
- [ ] service 命名规范与 schema 描述格式（能否直接生成 tool 定义？考虑与 MCP 的对齐程度）
- [ ] 模块是编译期静态注册还是运行时动态加载？
  > 单人项目，动态加载可能是过度设计——静态注册 + 清晰目录约定或许就够
- [ ] 跨模块编排住在哪一层？（中枢 agent，还是每模块自己声明「我关心什么事件」）
- [ ] `opt-in 暴露给 AI` 的粒度：模块级 / entity 类型级 / 单条记录级？
  > 关联 [DESIGN.md](../DESIGN.md) §6 #17——接理财时「默认不暴露」是会让人感谢自己的默认值
- [ ] 是否引入事件总线（HA 的心脏），还是单人规模下直接函数调用就够？

## 模块选择标准（**只定标准，不定顺序**）

下一个模块该满足：

1. **能验证跨域写入扇出** —— 一次输入落到多个系统（这是 harness 唯一挣得到饭的地方）
2. **加入成本 ≤ 第一个模块的 1/5** —— **这是检验架构对不对的唯一标准**；若依然很痛，说明在盖单体，应停下重构而不是硬上
3. **有现成开源对照可借** —— 别重造 Firefly III / Monica 已经做得更严谨的东西
4. ⚠️ **警惕「最上镜」陷阱** —— AI 卖点是纯模型能力（如合成穿衣照）、跨域数据协同薄的模块，最上镜却**最不能验证架构**，别拿它开路

## 验收标准

- 契约能**完整描述现有厨房模块**，无需为它开特例
- 照着契约能在**不改中枢代码**的前提下加一个新模块
- 加第二个模块的实测成本 ≤ 第一个的 1/5（若做了实测模块）

## 风险与不做什么

- ⚠️ **不要在没有第二个模块的真实需求前过度抽象**。只有一个实现的抽象一定是错的抽象
- **不做**连接外部开源系统（Firefly / Monica）的 adapter——那是更远的事，且要先知道两个代价：①是 N 个集成问题不是一个 ②统一体验的可靠性 = 最烂那个连接器的可靠性
- **不做**插件市场 / 动态加载
- **不定**模块顺序（本任务只产出标准）
