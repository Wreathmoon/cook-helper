## 目标

把 source of truth 从 Supabase **翻转**到本地 vault 文件，并用一个可丢弃的派生索引承担查询。

## 为什么做

这是「数据保存在本地、类似 Obsidian」这个已定短期目标的核心实现步骤（[FUTURE.md](../FUTURE.md) §1）。

**架构是 Obsidian 自己在用、但大家常忽略的那一层**——它并不是每次算反向链接就去 grep 全部文件，它有隐藏缓存：

```
磁盘纯文件（source of truth）  →  .index/ SQLite（查询层，可删可重建）
```

**为什么必须有派生索引**：推荐引擎的核心是 `库存 × 菜谱食材` 的 join（`src/lib/recommend/tiering.ts`），纯文件遍历撑不起来。索引进 `.gitignore`，删掉就重建，**不是真相**。

## 关键决策（待讨论）

这一条决定整个任务的规模，必须先定：

| 选项 | 后果 |
|------|------|
| **保留云端多用户版** | 数据层需要**双 adapter 抽象**（Supabase adapter / 本地文件 adapter），A 层 Service 签名要从 `fn(supabase, userId, args)` 改成 `fn(ctx, args)`。复杂度显著上升，但 `cook.wreathmoon.com` 继续可用 |
| **云端降级为只读 Demo** | 本地模式可**整块剥掉** Supabase Auth / RLS / 多租户 / OTP 注册 / 种子复制的 service_role 逻辑，代码大幅简化；但线上版本不再能注册使用 |

## 验收标准

- 删掉 `.index/` 后重启，索引自动重建，功能无差异
- 手工在编辑器里改一个 `.yaml` 里的 `stock_level`，刷新页面推荐结果随之变化
- 推荐结果与 Supabase 版本**对同一份数据完全一致**（回归基准）
- 写入过程中强制杀进程，vault 文件不出现损坏
- `npx vitest run` 全绿
