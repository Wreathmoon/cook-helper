## 目标

让用户能上传自己的菜谱、下载别人的菜谱、批量导入一份菜单——形成一个轻量社区。

## 为什么做

这是**这套架构里唯一真正需要中心化服务的部分**，也是让开源项目长出社群的抓手。

而它跟 [Task/05](./05-vault-format-spec-✅已完成.md) 是同一件事的两面：**菜谱上传 / 下载 / 批量导入必须先有一个纯文本菜谱格式。** 所以顺序很清楚——**先定格式，社区功能自然长出来**，不需要另设一套数据模型。

## 关键决策（待讨论）

- [ ] **托管形态**：最省的方案是**纯 GitHub**（菜谱文件放仓库，PR 即投稿，下载即 raw 文件）——零运维、零成本、天然版本管理、契合自托管人群习惯。对比自建服务（要账号、要审核后台、要运维）
  > 倾向 GitHub 方案。它还顺带解决了「谁来审核」——PR review 就是审核
- [ ] 分享粒度：单菜谱 / 菜单包（一组菜谱）/ 整个 vault
- [ ] 索引与检索：怎么找到想要的菜谱？（目录文件 / 标签 / 全文搜索）
- [ ] **分享行为，不只分享数据**（[DESIGN.md](../DESIGN.md) §12.3 借鉴点 7，对应 HA 的 blueprint）：除了菜谱，是否也分享推荐配置（`RECOMMEND_CONFIG` 权重）、食材别名表、AI prompt 模板？
  > 这是社区能不能活起来的关键差别——只分享数据的社区很快就静了
- [ ] 导入时的名称归一：下载的菜谱用词与本地库存不一致怎么办（依赖 [Task/06](./06-ingredient-name-normalization-✅已完成.md)）
- [ ] 是否需要「导入预览」：这道菜我现在缺几样？（这是最能激发下载欲的展示）

## ⚠️ 必须先想清楚的两件事

### 1. 菜谱内容的来源与版权

**食材清单本身基本不受版权保护，但菜谱的描述性文字 / 步骤散文是受保护的。** 用户从菜谱书、菜谱网站抄来的内容上传到社区，是一个真实的法律灰区。

需要的机制：

- 投稿时的**来源声明**（原创 / 改编自 X / 家传）
- 一条清晰的**下架流程**（收到申诉怎么处理）
- 明确的内容许可声明（用户上传的菜谱以什么许可发布）

> 别等到出问题才想。GitHub 方案的好处之一是 PR 阶段就能问「这是你写的吗」。

### 2. 审核与滥门槛

任何允许公开上传的东西都会收到垃圾内容。GitHub PR 模式天然有门槛；自建服务则必须先想清楚审核由谁做。

## 交付物

- 分享仓库 / 服务的形态与目录约定
- 上传（投稿）流程与来源声明
- 应用内的浏览 / 下载 / 批量导入 UI
- 内容许可与下架流程文档

## 操作步骤

> 待托管形态决策定稿后回填。

## 验收标准

- 能把本地一道菜谱导出成一个文件并投稿
- 能在应用内浏览、预览（含「我现在缺几样」）、一键导入
- 导入的菜谱立即参与推荐运算，且名称正确匹配到本地库存
- 每条社区菜谱都有来源声明
- 有可执行的下架流程

## 风险与不做什么

- ⚠️ **不要在没有内容许可与下架流程的情况下开放公开上传**
- **不做**用户账号体系 / 社交功能（点赞、关注、评论）——路径 A 不做平台
- **不做**从菜谱网站批量抓取导入种子（版权风险 + 违反 robots）
- **不做**任何形式的商业化（[DESIGN.md](../DESIGN.md) §1.4）
