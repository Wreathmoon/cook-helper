# 10 — 记忆层设计与实现

> **状态**: 决策已定稿（2026-08-04），可开工
> **依赖**: 05
> **被依赖**: 12 —— ⚠️ **本任务不含任何记忆生效逻辑**，见决策 ③
> **阶段**: 记忆层

## 目标

让系统能记住「我不吃辣」「这个月想少吃肉」这类跨域偏好，并把它们**可靠地、可解释地**作用到推荐上。

## 为什么做

「不吃辣」「这月少吃肉」**不属于任何单个模块**——它是跨域的、随时间沉淀的，是让 agent 感觉「它认识我」的**唯一**来源。

> **这是本项目唯一真正独有的资产。** 菜谱可以借（Mealie 有）、记账可以借（Firefly 有）、连接器只是水管——而「关于你这个人」的这层记忆，只能自己长出来。

而且它恰恰**最适合做成真·Obsidian 式本地 Markdown**：纯文本、可 grep、用户能自己打开改删——**这就是信任的全部来源**。

## 文件格式（草案）

一条记忆一个文件 + 一个索引。位置：`vault/memory/`。

```markdown
---
id: 01J9AB3C
type: preference          # preference(长期偏好) | goal(临时目标) | constraint(禁忌/过敏)
scope: [kitchen]          # 或 [global]，决定哪些模块能看到
source: stated            # stated(用户明说) | inferred(agent 推断)
confidence: high
enforcement: soft         # soft(倾向) | hard(要求模型排除) —— 见下方 ⚠️
created: 2026-07-25
expires: null             # goal / constraint 必须给日期
status: active
---
不吃辣。推荐时排除「中辣」「重辣」；「微辣」先问一句。
```

过敏 / 禁忌是 `type: constraint`，格式相同——**这类字段默认就在格式里，不是可选扩展**：

```markdown
---
id: 01J9AB4D
type: constraint
scope: [kitchen]
source: stated
confidence: high
enforcement: hard
created: 2026-08-04
expires: null
status: active
---
花生过敏。含花生、花生油、花生碎的菜一律排除。
```

> ⚠️ **`enforcement` 的含义在 2026-08-04 变了。** 原先 `hard` 表示「在代码里过滤」，
> 现在**两个值都只是给模型的信号**——`hard` 是「要求排除」，`soft` 是「倾向」。
> 代码不再依据这个字段做任何分支（决策 ③④）。字段保留，是因为它对模型仍是有用的强度提示。

索引 `vault/memory/index.md`——一行一条，全量读进来（很小）：

```markdown
- [不吃辣](no-spicy.md) — 排除中辣重辣，微辣需询问
- [这月少吃肉](less-meat-2026-07.md) — 至 2026-07-31，素菜加权
```

### 三个字段是骨架，缺一个就会烂

- **`type` 决定生命周期**
  - `preference` 长期有效
  - `goal`（这月少吃肉）**必须带 `expires`**，否则三个月后它还在悄悄压着推荐
  - `constraint`（术后软食、过敏）同样带失效期
  > ⚠️ **不区分这三种，是个人 AI 记忆系统最常见的死法**——记忆只增不减，慢慢把推荐悄无声息地毒化。而且毒化过程没有报错、没有征兆，等你发现推荐变差时已经找不到原因。

- **`source` + `confidence` 决定信任** — agent 推断出来的必须可被用户一键否掉

- **`scope` 决定跨域** — 「不吃辣」只管厨房；「我是极简主义者」可能同时影响衣柜 + 订阅 + 厨房

## ⚠️ 现状核实（2026-08-04，实测）

动笔前核实了本文档引用的每一处代码，**四处与现实不符**，其中两处会把实现直接带偏：

| 文档原说法 | 实测 |
|-----------|------|
| hard 过滤在 `tierRecipes` | ❌ **筛选器全在 `scoreAndSort` 开头**（`src/lib/recommend/scoring.ts:21-52`）。`tiering.ts` 里没有任何 filter 概念，它只算「食材齐不齐 → 分档」 |
| 「现有权重已占满 1.0，加维度要重新分配」 | ❌ **权重是动态归一化的**（`scoring.ts:120-122`：`totalWeight = weights.reduce(...)` 后相除）。每个维度只在适用时才 push，四个数和为 1.0 是巧合。**加维度不用动前四个** |
| `reason` 最多 4 条，在 `types/index.ts:106` | ❌ 在 **`:115`**，类型是 `reason?: string`（**单数**）；`HeroCard.tsx:30` 上限是 **3 条**，且 `rec.reason` push 在最后会被切掉 |
| 「缺失维度优雅降级」可直接复用 | ❌ 语义是反的。现有筛选器缺字段就**放行**（`scoring.ts:34/46`），且是**相等**语义（`spiciness === 用户选的`），表达不了「排除中辣和重辣」 |

**种子数据实测**（54 道菜谱）：

| 属性 | 覆盖率 |
|------|--------|
| `spiciness` | 54 / 54（不辣 36 · 微辣 11 · 中辣 5 · 重辣 2） |
| `diet_type` | 54 / 54 |
| `nutrition` | **0 / 54** |
| `cuisine` | **0 / 54** |

> `nutrition` 零覆盖值得单独注意：`scoring.ts:108-110` 的营养搭配维度会读它，
> 实际只能靠 `diet_type` 那条分支生效。不属本任务范围，但别在此基础上叠新逻辑。

**而食材型判断的数据根本不存在**——`seed/kitchen/recipes/宫保鸡丁/recipe.md` 的食材表没有花生，
`inventory/` 里也没有「花生」。这条直接推翻了原方案，见决策 ③。

## harness 四件事

### ① 检索：明确不上向量库

量级是**几十到几百条**。在这个规模上，**关键词 + scope 过滤完胜 embedding，而且可调试**。

做法：`index.md` 全量读入 → 按 `scope` 命中当前域的 + `global` 的 + `status: active` 的 → 展开成完整文件。

> 上向量数据库是这里最典型的过度工程（见 [DESIGN.md](../DESIGN.md) §13 反模式 3）。

### ② 注入：全部交给 LLM + 明示免责

**所有记忆（含过敏、禁忌）统一渲染进 system prompt 的「关于你」区块，由模型做选择与排除判断。本任务不写任何记忆过滤代码。**

> ⚠️ **战略纠正（2026-08-04）**
>
> 本节原文规定：soft 偏好进 `scoring.ts` 评分，**hard 约束（过敏、医疗禁忌）在 `tiering.ts` 里过滤掉，让模型根本看不到那些菜谱**，理由是「提示词遵从性永远不是 100%，把过敏原交给『希望模型记得』是不可接受的」；并称「好消息：现有 A/B 分层天然支持这个，不用新建机制」。**整段已废弃。**
>
> **理由（两条，第一条是致命的）**：
>
> 1. **数据撑不起代码判断。** 宫保鸡丁的食材表里没有花生，`inventory/` 里也没有「花生」这个食材。食材表记的是冰箱库存、服务于采购，不是配料表——没人会录「一勺花生油」。所以代码过滤在过敏这件事上只会**确定性地把宫保鸡丁推给花生过敏的用户**。确定性的代码 + 残缺的数据 = 确定性的错误答案，而且比模型出错更危险，因为它看起来可靠、用户会依赖它。
> 2. **「不用新建机制」不成立。** 现有筛选器不在 `tiering.ts` 而在 `scoring.ts:21-52`，且是相等语义，表达不了「排除中辣和重辣」。
>
> **因此**：过敏与禁忌作为记忆字段默认存在，判断交给 LLM，并在设置页明示不保证准确、请用户自行核对成分。
>
> **仍然成立的那半句**：**提示词遵从性永远不是 100%。** 区别是现在它成了**对用户明示的已知限制**，而不是一个假装被代码解决掉的问题。

### ③ 写入：agent 提议，用户确认

记忆写入是**显式**工具调用（`remember(...)`），且**新记忆要露出来给用户看一眼**。

> 悄悄记下一条推断错的记忆、然后用它默默影响半年的推荐——这是这类产品让人觉得「阴间」的第一大来源。解药就是 Obsidian ethos：那是一个 markdown 文件夹，用户随时能打开改删。

### ④ 复盘：让记忆可解释

现有 UI **已经埋好了坑**——推荐主推卡上有「**为什么推荐它：**」+ 最多 4 条理由（`RecommendedRecipe.reason`，`src/types/index.ts:106`）。

**把命中的记忆直接写进那几条理由里**：

> 「你说过不吃辣，已避开川辣类」

一举解决三件事：可解释性、用户发现记忆错了、AI 价值可被感知。

> 为规则引擎做的那个「为什么推荐它」，恰好是 AI 记忆最好的展示位。

## 关键决策（2026-08-04 全部定稿）

- [x] **① 手工维护还是一上来接 AI 写入** → **先手工**。用户自己写 markdown，UI 提供列表与删除。不依赖 [Task/12](./12-ai-command-layer.md) 就能交付。
- [x] **② `soft` 偏好落在哪** → **问题作废。** 原问题预设了「记忆进评分权重」，而决策 ③ 已把全部判断交给 LLM，代码侧不新增任何评分维度。
  > 附带纠正：原注释说「权重已占满 1.0，加维度要重新分配」是**错的**——`scoring.ts:120-122` 会按实际用到的权重动态归一化。这条留在这里备查，将来真要加维度时不必重新分配。
- [x] **③ 过敏 / 禁忌怎么保证** → **不由代码保证。** 记忆格式默认带过敏、禁忌字段，但**判断全部交给 LLM**，配一份免责声明明示不保证准确、请用户自行核对成分（口径参照大模型「不提供医疗建议」）。推翻了原「hard 约束进代码」方案，论证见上方纠正块。
- [x] **④ 所有记忆都走 LLM，还是能映射到字段的走代码** → **全部走 LLM。** 不做代码/模型双路径。
  > **已知代价（作者知情并接受）**：没配 API key 时记忆**完全不生效**。记忆层因此成为项目第一个需要 key 的功能（[DESIGN.md](../DESIGN.md) §6 #21）。一期全部功能（库存、菜谱、日历、规则推荐）仍然无 key 可用，这条原则的范围被限定，不是被推翻。
- [x] **⑤ 没配 key 时怎么显示** → 这些记忆必须标成**「未生效 —— 需配置 API key」**，不能混在生效列表里。用户以为过敏记忆在保护自己、实际什么都没发生，是本任务最不可接受的失败态。
- [x] **⑥ `expires` 到期谁触发** → **读取时过滤，绝不改用户的文件。** 过期记忆不进检索结果，文件原样留着；UI 单独列「已过期」区让用户自己决定删不删。
  > 起个定时任务去改用户的 markdown，等于半夜动别人的文件——这是这类产品「阴间」的第二大来源。ethos 是「那是你的文件夹」，只读不偷改。
- [x] **⑦ 记忆管理 UI 做多深** → **只读列表 + 删除**。新增和编辑引导用户直接改 `vault/memory/*.md`。
  > 信任来自「文件是你的」，不是「我给你做了个好用的编辑器」。删除必须在系统里能做（看到错的记忆当场要能否掉）；新增本质是写文档，交给文本编辑器更符合叙事。9 个 frontmatter 字段做成表单要配校验、枚举、日期选择，为几十条数据不划算。
- [x] **⑧ 记忆理由被 `slice(0,3)` 切掉** → **给记忆留固定槽位**：上限仍是 3，命中时记忆占第一格，挤掉信息量最低的「快手菜」（耗时在卡片上已另有显示）。改动只在 `buildReasons()` 内部，类型不动。
  > 现网实测：凉拌菠菜的三格已被「菠菜已放多天 / 食材全齐 / 快手菜只需10分钟」占满，记忆理由排第四必被切——**恰好在最需要解释的清库存档上不可见**。可解释性是记忆层的核心卖点，「大部分时候可见」等于没做。`reason` 将来若需多条同时展示，`string → string[]` 任何时候都能改，不是单向门。
- [x] **⑨ `scope` 取值空间** → **只有 `kitchen` 和 `global`**。现在只有厨房一个模块，为不存在的模块设计分类法是 [DESIGN.md](../DESIGN.md) §13 反对的过度工程。等 [Task/13](./13-module-contract.md) 模块契约定稿再扩。
- [x] **⑩ 记忆冲突（「不吃辣」vs「想试试川菜」）** → **不做冲突引擎。** 决策 ④ 之后冲突判断天然属于模型职责，代码侧没有可仲裁的地方。
- [x] **⑪ `inferred` 要不要先确认** → **本任务不涉及。** v1 全部 `source: stated`，没有 inferred 记忆产生；该问题随自动推断一并归 [Task/12](./12-ai-command-layer.md)。
- [x] **⑫ 只读沙盒要不要带记忆** → **带，但只展示列表与免责声明，不展示效果。**
  > 原问题写的是「要不要参与 `/demo`」，而 `/demo` 页已在 [Task/04](./04-single-user-local-✅已完成.md) 删除，现在是只读沙盒。
  > **注意期望值**：沙盒没有 API key（也不该有——BYOK，且公开实例放 key 会被滥用），所以记忆在沙盒里**不影响推荐**。它能展示的是「记忆长什么样、系统记得什么、免责声明说了什么」，展示不了「记忆如何改变推荐」。这削弱了原先「演示 AI 记忆很有说服力」的判断，但列表本身仍值得展示。

## 验收标准

- 手写一条记忆文件 → 出现在管理页「生效中」分区
- 一条带 `expires` 且已过期的 goal → 出现在「已过期」分区，**且检索纯函数不返回它**，**且文件未被程序修改**（比对 md5）
- 未配 API key 时，过敏 / 禁忌记忆显示「未生效 —— 需配置 API key」
- 免责声明在记忆管理页可见，明确包含「不保证准确、请自行核对成分」
- 用户能在 UI 里删掉任意一条记忆，删掉后列表立即更新
- `buildReasons()` 在传入记忆理由时，该理由**必定出现在 3 条内**（含被「清库存 + 全齐 + 快手菜」占满的用例）
- `npx vitest run` 全绿（含检索过滤、`expires` 读时过滤、`buildReasons` 槽位的新测试）

> ⚠️ **本任务验收不包含「记忆改变了推荐结果」**——决策 ④ 之后那需要 LLM，属 [Task/12](./12-ai-command-layer.md)。
> 原验收第一条「写一条 hard 的『不吃辣』→ 中辣重辣不出现在推荐里」已随决策 ③ 作废。

## 风险与不做什么

- ⚠️ **最不可接受的失败态：用户以为过敏记忆在保护自己，实际什么都没发生。** 免责声明（决策 ③）与「未生效」标注（决策 ⑤）是这条的解药，**两个都不能省**
- ⚠️ **不要起定时任务去改用户的 markdown**（决策 ⑥）。`expires` 只在读取时过滤
- **不做**代码级记忆过滤（决策 ③④ 已推翻原方案）
- **不做**向量检索
- **不做**记忆的新增 / 编辑表单（决策 ⑦，只做列表 + 删除）
- **不做**跨设备记忆同步（走 BYO，见 [Task/08](./08-local-data-layer.md)）
- **不做**自动推断记忆（第一版全部 `source: stated`），推断留给 [Task/12](./12-ai-command-layer.md)

> ⚠️ **本节曾有一条相反的规定**：「**hard 约束的实现必须是确定性的代码过滤**。任何『把过敏信息写进 prompt 然后相信模型』的实现都不可接受，即使它看起来能工作」。
