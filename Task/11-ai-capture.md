# 11 — AI 录入折叠（拍照 / 小票 / 语音 → 结构化写入）

> **依赖**: 06, ~~07~~ → **04**

> **阶段**: 二期 AI

## 目标

把「维护数据」这件事的成本压到接近零：拍一张照、说一句话，库存和日历自己就更新了。

## 为什么做

**这是二期真正的主角，也是整个产品能否长期活下去的关键。**

论证链（见 [DESIGN.md](../DESIGN.md) §1.5）：

1. 唯一失败模式是**作者自己弃用**
2. 根因是**数据变馊**——维护录入是无偿劳动，而这正是人类最讨厌的事
3. Pantry tracker / meal planner 品类的坟场就是这么堆起来的（Mealie / Grocy 的共同天花板也正是「录入极重」）
4. 三档库存制只是缓解，仍要求每次买菜、每顿饭后手动点
5. **所以：只有 AI 能把录入成本压到接近零 —— AI 不是威胁，是这个产品的救命稻草**

> 对比一下就清楚了：「对话取代界面」是**为了炫而找问题**；「无摩擦录入」是**真实的、未被开垦的需求**。枪口必须对准后者。

## 场景（按价值排序）

| # | 场景 | 输入 | 输出 |
|---|------|------|------|
| 1 | **买菜回来** | 一张购物袋 / 冰箱照片 | 批量识别食材 → 建议档位改 `enough` → 用户确认 |
| 2 | **小票入库** | 一张超市小票 | 解析条目 → 归一化名称 → 批量入库 |
| 3 | **做完饭** | 一句话「我做完了宫保鸡丁」 | 写日历 `completed` + 弹出该菜食材的档位调整 |
| 4 | **随手记** | 「西红柿没了」 | 直接改档位 |

> **远期的杀手锏在写入侧**：一次自然语言输入**扇出到多个系统**（「我买了双鞋 800」→ 衣柜 + 账本 + 资产三处同时动）。厨房模块是这个模式的第一次验证。

## 关键决策（待讨论）

- [ ] **先做哪一个场景？** 建议从 **3（做完饭）** 开始——它不需要视觉识别，纯文本意图 → 已有的 `completeEntry` service，最短闭环、最快验证价值
- [ ] 模型与 provider 选型：需支持什么能力（图像输入 / 结构化输出 / function calling）、成本、延迟。**实施时须查当时的官方 API 文档确认可用模型与参数**，不要照抄本文档
- [ ] 图片处理在端上还是服务端？（关系到 BYOK 时 key 会不会暴露给浏览器）
- [ ] **识别结果如何确认？** 必须是「AI 提议 → 用户过一眼 → 落库」，还是高置信度可直接落库？
  > 倾向：**一律确认**。批量误写库存会直接毁掉推荐质量，而推荐质量是产品的全部价值
- [ ] 归一化怎么接：AI 输出的原始名称 → [Task/06](./06-ingredient-name-normalization-✅已完成.md) 的归一层 → 匹配不上的怎么处理
- [ ] 无 API key 时的降级：全部功能保持手动可用（这是硬要求）

## 验收标准

- 目标场景的录入时间比手动**至少快 3 倍**（这是这个任务存在的唯一理由，做不到就是失败）
- 每次 AI 写入前用户都看到了将要发生什么
- 无 API key 时全部手动路径完好无损
- 识别错误可一键撤销

## 风险与不做什么

- ⚠️ **AI 批量写库存是破坏性操作**。没有「确认 + 可撤销」不要上线
- **不做** `/chat` 独立聊天页（[DESIGN.md](../DESIGN.md) §1.3 已废弃该方案）
- **不做**跨模块扇出——现在只有厨房一个模块，扇出等有了第二个模块再说（[Task/13](./13-module-contract.md)）
- **不做**语音识别的自研，若要语音优先用现成 API
