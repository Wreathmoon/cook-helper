## 目标

实现 vault 纯文本格式与现有 Supabase 数据之间的**双向、无损**转换。做完之后：「你的数据是你的，随时能导出成纯文本，也能改完导回去。」

## 为什么做

这是 [FUTURE.md](../FUTURE.md) §1.7「**先定格式，再搬家**」的落地动作——**不重写数据层，只在边界加导入导出**。

它同时是三件事的前置：

- **本地化叙事成立**：路径 A 的 ethos 拿到 90%，成本只有重写的 10%
- **社区分享**（[Task/14](./14-community-sharing.md)）：上传 / 下载 / 批量导入菜谱走的就是这套解析器
- **AI 录入**（[Task/11](./11-ai-capture.md)）：AI 产出结构化数据后，走同一条写入路径

## 关键决策（待讨论）

- [ ] 导出粒度：全量 vault / 按模块 / 单个菜谱（社区分享需要单菜谱粒度）
- [ ] 导入冲突策略：同 ID 或同名已存在时——覆盖 / 跳过 / 新建副本 / 交互式选择？
- [ ] 导入是否**事务性**（全成功或全回滚）？部分失败怎么报告？
- [ ] 照片怎么处理：导出时从 Supabase Storage 下载成真实文件？导入时上传？还是只导路径引用？
- [ ] 导出的交付形态：zip 下载 / 写入用户选定目录（File System Access API，仅桌面 Chrome）/ 命令行脚本？
- [ ] 是否需要 dry-run 模式（先报告「将导入 N 道菜谱、M 个冲突」再执行）？
  > 倾向：**需要**。导入是破坏性操作，无预览的批量导入很容易毁数据

## 交付物

- 解析器 / 序列化器（建议 `src/lib/vault/`）：`parseRecipe` / `serializeRecipe` / `parseInventory` / …
- Server Actions：`exportVault` / `importVault`
- UI 入口（设置页或独立页面）
- 单元测试 + **往返测试**（round-trip）

## 操作步骤

> 待 [Task/05](./05-vault-format-spec-✅已完成.md) 定稿后回填。

大致方向：

1. 写解析 / 序列化纯函数，用 Task/05 产出的 `docs/vault-examples/` 作 fixture
2. **先做导出**（只读，无风险），人工检查产物可读性
3. 再做导入，先实现 dry-run 报告，再实现落库
4. 写往返测试：`DB → vault → DB`，断言语义等价
5. 接 UI

## 验收标准

- **往返无损**：现有真实账号数据导出为 vault、再导入到空账号，两边语义完全一致（菜谱数、食材数、关联关系、attributes、照片）
- 手写的 `docs/vault-examples/` 能被正确导入
- 导入前有预览 / dry-run，导入失败有明确的逐项错误报告
- `npm run build` 无错误、`npx vitest run` 全绿（含新增往返测试）

## 风险与不做什么

- ⚠️ **导入是破坏性操作**。必须有 dry-run，且**先在测试账号跑通再碰主账号**
- **不做**本地文件读写（那是 [Task/08](./08-local-data-layer.md) / [Task/09](./09-local-web-service-✅已完成.md)）；本任务的导出产物是「下载下来的一堆文件」，不是「App 直接读的目录」
- **不做**社区上传（[Task/14](./14-community-sharing.md)）；本任务只提供它需要的格式能力
